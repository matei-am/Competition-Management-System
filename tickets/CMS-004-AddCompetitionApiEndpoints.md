# CMS-004: Add Competition API Endpoints

**Epic:** EPIC-003
**Status:** In Progress
**Blocked by:** CMS-003

## Objective

Create a thin REST API vertical slice for Competition CRUD operations. The controller maps HTTP requests to the Application service and maps service outcomes to HTTP responses while reusing the existing Domain and Infrastructure behavior through the Application boundary.

## Acceptance Criteria

- [ ] `CompetitionsController` is created in `src/CompetitionManager.Api/Controllers/CompetitionsController.cs` with route `api/[controller]`.
- [ ] The controller depends on `ICompetitionService`; the Application service implements that interface.
- [ ] `GET /api/competitions` returns all competitions with HTTP 200.
- [ ] `GET /api/competitions/{id}` returns the competition with HTTP 200, or HTTP 404 for `NotFoundException`.
- [ ] `POST /api/competitions` returns HTTP 201 with the created response and a `Location` header generated by `CreatedAtAction`.
- [ ] `PUT /api/competitions/{id}` returns HTTP 200 with the updated response and preserves partial-update semantics.
- [ ] `DELETE /api/competitions/{id}` returns HTTP 204, or HTTP 404 for `NotFoundException`.
- [ ] `ArgumentException` and `InvalidOperationException` from the Application service become HTTP 400 responses.
- [ ] Unexpected exceptions are not caught or misclassified by the controller and reach host-level HTTP 500 handling.
- [ ] Existing Application DTOs are reused without duplicating Domain business logic in the controller.
- [ ] Controller tests pass and the architecture validator reports no forbidden dependencies.

## Layer Breakdown

### Domain
- No code changes. The controller relies on the existing `Competition` aggregate and Domain rules through the Application service.

### Infrastructure
- No code changes. The API must not reference `CompetitionRepository` or any other Infrastructure implementation.

### Application
- Add `ICompetitionService` and have the existing `CompetitionService` implement it.
- Reuse `CreateCompetitionRequest`, `UpdateCompetitionRequest`, and `CompetitionResponse` from the Application layer.

### API
- Add `src/CompetitionManager.Api/Controllers/CompetitionsController.cs`.
- Add controller registration and `MapControllers()` in `Program.cs`.
- Register `ICompetitionService` to resolve `CompetitionService`.
- Implement `GetAllCompetitions`, `GetCompetitionById`, `CreateCompetition`, `UpdateCompetition`, and `DeleteCompetition`.

## Implementation Notes

- **Thin controllers:** The controller validates HTTP shape, maps DTOs, calls the Application service, and returns HTTP responses. It does not enforce Domain rules.
- **HTTP semantics:**
-  - POST: return `CreatedAtAction(nameof(GetCompetitionById), new { id = response.Id }, response)`.
  - GET: return 200 OK with the response body.
  - PUT: return 200 OK with the updated response body.
  - DELETE: return 204 No Content.
  - 404 Not Found for `NotFoundException`.
  - 400 Bad Request for `ArgumentException` and `InvalidOperationException`.
- **Error handling:** Translate known Application exceptions at the controller boundary; allow unexpected exceptions to reach host-level 500 handling.
- **Attribute routing:** Use `[HttpGet]`, `[HttpGet("{id}")]`, `[HttpPost]`, `[HttpPut("{id}")]`, and `[HttpDelete("{id}")]`.
- **Dependency injection:** Keep the repository registration required by `CompetitionService` and register the interface-to-service mapping.
